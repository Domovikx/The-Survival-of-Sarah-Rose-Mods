# Скорость бэкенда перевода: что пробовали и чем кончилось

Замеры 2026-11-16 на живом бэкенде перевода. Вопрос был: можно ли ускорить
перевод, не потеряв качество (качество — приоритет №1, скорость №2).

## Стенд

- Модель: `Index-Translate-9B.Q4_K_S.gguf` (LM Studio backend `llama.cpp` 2.54.0).
- Команда бэкенда (базовая, она же рабочая):

  ```text
  llama-server -m Index-Translate-9B.Q4_K_S.gguf -c 8192 -np 4 -ngl 99 \
    --host 127.0.0.1 --port 8081 --alias index-translate-9b --no-webui
  ```

- Нагрузка: `translate_run.mts es --improve 400` — те же 400 первых строк `es`,
  тот же промпт, 8 воркеров, `temperature 0`. Ничего в `po` не пишется
  (`--improve`), сравнивались только тексты и время.
- Каждый режим прогнан ДВА раза.

## Важная особенность: `temperature 0` не детерминирован

Два прогона с ОДИНАКОВЫМ конфигом дают разный текст: из 281 переписанной
строки совпали 206, различаются 75 (27 %). Причина — непрерывный батчинг
llama.cpp: состав батча меняет порядок операций, и логиты «плывут» в пределах
допуска. Вывод для будущих A/B: **побайтовое сравнение здесь неприменимо**,
сравнивать можно только время/ток-в-секунду и смысл (ревью/судья).

## Результат: `--spec-type ngram-simple` (вариант C, без второй модели)

| режим                      | время на 400 строк | мс/токен (генерация) | tok/s |
| -------------------------- | ------------------ | -------------------- | ----- |
| база (без спекуляции)      | 167 с и 157 с      | 7.74                 | 129.2 |
| `--spec-type ngram-simple` | 162 с и 169 с      | 8.01                 | 124.9 |

- Draft acceptance — **0.66** (принято 2/3 предложенных токенов), то есть
  механика работает.
- Итог по скорости — **в пределах шума, фактически на 3 % ХУЖЕ**: выигрыш от
  принятых токенов съедается стоимостью поиска n-грамм на CPU и лишними
  проверками (принятые серии короткие, mean len 1–3 токена).

**Решение: вариант C не используем.** Рабочий конфиг остаётся базовым (без
`--spec-type`). Качество при этом не при чём: спекулятивное декодирование
проверяется целевой моделью (lossless по построению), отказ — только из-за
отсутствия выигрыша.

## Что осталось непроверенным (и чего ждать)

| вариант                                    | что это                                                    | ожидание | цена                                                      |
| ------------------------------------------ | ---------------------------------------------------------- | -------- | --------------------------------------------------------- |
| A. draft-модель другого размера            | `-md Qwen3.5-0.6B.Q8_0.gguf` (то же семейство/токенизатор) | +30–60 % | +0.5–1 ГБ VRAM, качать ~0.5 ГБ                            |
| B. тот же Index-Translate в меньшем кванте | target `Q4_K_S` + draft `Q2_K/Q3_K`                        | +5–15 %  | качать 2–3 ГБ; draft почти такой же медленный, как target |

Вариант A — единственный с реальным потенциалом. Проверять только когда
появится время и после того, как корпус переводов стабилизируется: выигрыш
30–60 % на 69 тыс. строк × 8 языков — это часы.

## Побочные факты, снятые по ходу

- `-c 8192 -np 4` → **2048 токенов контекста на слот**. Промпты перевода
  (3 реплики до + 1 после + правила + ответ) влезают, но запас тонкий.
  `-np 2` даёт 4096 на слот (медленнее по числу параллельных запросов).
- **Докупать оперативку ради скорости перевода смысла нет**: модель целиком в
  VRAM (`-ngl 99`), скорость определяют GPU и VRAM. RAM влияет только на
  отсутствие свопа, скорость холодной загрузки модели и на возможность держать
  рядом IDE + два браузера. Текущее потребление: llama-server ~13 ГБ RAM
  (16 ГБ private), свободно 3–4 ГБ из 31.
- Прогноз цен на DDR5 (ноябрь 2026): 16-Гбит чип $8.70 (окт 2025) → $48
  (сен 2026); производители говорят «2027 не легче», баланс — не раньше второй
  половины 2028. Апгрейд — по потребности, не по прогнозу.

## Как повторить замер

```bash
# 1) бэкенд нужного конфига (менять ТОЛЬКО --spec-* / -md)
llama-server -m <...>/Index-Translate-9B.Q4_K_S.gguf -c 8192 -np 4 -ngl 99 \
  --host 127.0.0.1 --port 8081 --alias index-translate-9b --no-webui

# 2) два прогона на одних и тех же строках, время — по часам
node .opencode/skills/translate/translate_run.mts es --improve 400
# тексты складываются в tmp/translate_es.improve.log

# 3) объективная метрика из лога бэкенда (шум меньше, чем по времени):
grep -oE "eval time =\s+[0-9.]+ ms /\s+[0-9]+ tokens \(\s+[0-9.]+ ms per token" tmp/llama_*.log
```
