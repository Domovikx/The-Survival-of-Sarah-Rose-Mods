# [2026-10-30] Ресёрч: параллельные процессы генерации озвучки vs последовательные

Статус: DOING

## Задача от пользователя

«а еще подумать нельзя ли запускать паралельно процессы не ускорит ли это процесс или же
остаемся только на последовательном сценарии, это надо проверить протестировать и взять в
работу, можем оформить таску для этой задачи, думаю будет полезно» (2026-10-30, на фоне
задачи Vox-озвучки трёх арок на 11 языках).

## Цель

Когда массовая генерация (≈19 000 файлов Vox + дальнейшие арки) идёт последовательно одним
процессом, а железо — RTX 5070 Ti 16 ГБ (CUDA), — выяснить замером, даёт ли запуск
нескольких процессов генерации реальное ускорение или упирается в GPU/VRAM, и принять
обоснованное решение «параллельно N=… / только последовательно» для планировщика
очередей. Критерий: таблица вариантов с замеренными цифрами (RTF, ускорение, VRAM,OOM-случаи) и записанное в задачу-решение, а не мнение.

  venv `C:/tools/voxcpm2`); оркестратор TS `voice_batch.mts`, стенд `voxcpm_bench.mts`.
- Текущие очереди: `voice_queue.sh {ru|en}` + `voice_ctl.py` (старт из voice-start.cmd
  запускает «обе очереди») — НЕ ясно, идут ли ru/en процессы одновременно или
  последовательно (проверить фактическое поведение, шаг 1); в очереди нет `--engine`
  (только cosy).
- Прецедент параллельного прогона: два процесса `voice_design.py` по
  OMP_NUM_THREADS=8 (~8 ГБ RAM на процесс) — так писали кандидатов голосов; на GPU

- Ранее (бенч 2026-10-24, `archive/2026-10-24-voice-engine-update-benchmark.md`):
  VRAM-конкуренция LLM и однопроцессность — часть прошлых выводов; НО конкретного

## Что сделать (ресёрч, по протоколу `tasks/AGENT.md`)

1. **Факт, а не память**: как устроен текущий запуск — voice-start.cmd/voice_queue.sh
   запускают ru и en одновременно? Идёт ли `OMP_NUM_THREADS`/CUDA-контекст на каждый
   процесс? Читать скрипты, зафиксировать в журнал.
2. **Вебсёрч** (2–3 запроса): параллельный инференс на одном GPU — несколько процессов vs
   один с batching; как ведут себя CUDA-процессы при конкуренции за GPU (time-slicing vs
   MPS на Windows); опыт параллелизации TTS/LLM-инференса (PyTorch, VoxCPM/CosyVoice
   issues). Приоритет: официальные доки → issues/исходники → замеры. Каждый факт —
   ссылка + дата.
3. **Замер** (обязателен, выборка ≥30 фраз, оба движка, которых касается задача):
   - A: 1 процесс, последовательно (baseline, RTF и с/файл);
   - B: 2 процесса × те же фразы (равномерная нарезка);
   - C: при необходимости 3 процесса (стоп по OOM/деградации).
     Замерять: суммарное время, RTF, ускорение относительно A, потребление VRAM/RAM
     (nvidia-smi), деградации (битые/пустые файлы, падения). LM Studio в этот момент —
     выгружен (иначе результат ложится под конкуренцию), либо отдельная серия «с LM Studio»
     как факт для планировщика ночного прогона.
4. **Таблица вариантов** (минимум 2) по критериям AGENT.md: ускорение, стабильность/OOM,
   цена в пайплайне (правки очередей), проверяемость, влияние на качество (не должно
   меняться — детерминизм по seed проверить: байты = baseline?). Метод исключения со
   ссылками на замер.
5. **Решение** записать в эту задачу: «параллельно N=… при … / последовательно», условия,
   при которых решение перестаёт быть верным (новый GPU, рост VRAM-требований). Если
   сомнение живо после 2 кругов — `[СОМНЕНИЕ: …]` владельцу.
6. **Применить в работе** (после решения владельца): нужные флаги/очереди в планировщик
   Vox-задачи (`2026-10-30-vox-storybeg-warc-11langs.md`, шаг 2) — только то, что
   подтвердил замер (YAGNI: нет решения «на вырост»).
