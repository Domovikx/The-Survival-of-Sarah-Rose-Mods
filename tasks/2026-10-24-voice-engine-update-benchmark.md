# [2026-10-24] Ресёрч+бенч: обновление движка озвучки (torch/TRT/конфиг) — протокол сравнения «до/после»

Статус: READY
Приоритет: **ВЫСОКИЙ** (впереди минимум 100к фраз озвучки — скорость = дни GPU)

## Задача от пользователя

«эм... но это же не всё что я собираюсь озвучивать ) если так вопрос поставить что нам еще
придется минимум 100к озвучить , тогда скорость имеет значение ? )

тогда предлагаю ставить задачу, записывать в нее ресерч или дособирать ресерч обновления
движка озвучки и его конфигурация и проготы тестовые, чтобы сравнить что было и что например
новое, посмотреть разницу в той же озвучке и может примерно хотя бы в скорости, как было и
как стало. пока формируем задачу»

## Цель

Когда впереди ≥100к фраз, я хочу закрытый ресёрч «обновлять ли движок озвучки (torch,
рантайм, конфигурацию)» с воспроизводимым тест-протоколом и числами «до/после» — скоростью
и качеством звука на одной и той же выборке фраз, — чтобы решение обновлять/не обновлять
принималось по замеру, а не по ощущениям. Критерий «стало лучше»: в задаче лежат базовый
замер («что было»), результат A/B по каждому кандидату («что стало») и вердикт с плюсами/минусами
в процентах; при равной цене — решение «не трогать» тоже результат.

## Что сделать (ресёрч, по протоколу `tasks/AGENT.md`)

1. **Вебсёрч (первоочередной, 403 был временным):** совместимость torch 2.14.x с python 3.10
   и CosyVoice (issues/discussions), что реально даёт TRT-рантайм для CV3 на Blackwell,
   свежие бенчи eager-vs-compile-vs-TRT для autoregressive TTS; обновить факты, если 403 прошёл.
2. **Матрица кандидатов (варианты для сравнения):**
   - A = база: текущий стек как есть (замер уже частично есть — «Контекст»);
   - B = torch 2.14.1+cu130 (+совместимые transformers) в изолированном венве (текущий НЕ
     трогать — параллельный venv, сравниваем);
   - C = TRT/Triton-рантайм (если ресёрч подтвердит поддержку CV3);
   - D = конфиг-эксперименты без смены звука (приоритет/потоки/3-й процесс/ffmpeg-пул/
     диагностика простоев) — каждый пунктом отдельно.
3. **Тест-протокол (ключевой артефакт задачи):**
   - Выборка: 50–100 фраз из POT (смесь длин/тонов/эмоций/спикеров, включая уже озвученные —
     для пары «старый корпус vs новый стек»), фиксированный seed.
   - Скорость: фраз/ч (часовой срез), с/фразу p50/p90, RTF — одинаковая методика для всех
     кандидатов; **замеры гонять, когда судья po-перевода НЕ на GPU** (иначе шум).
   - Качество: (а) объективно — WER/CER через Fun-ASR-Nano + SS через campplus (как upstream);
     (б) A/B-слушание пар «одна фраза, два стека» вслепую; (в) наш LLM-судья — только если
     методика даст воспроизводимые баллы.
   - Стабильность: падения/ретраи/`.part`-сироты на 1000 фраз.
4. **Применение:** вердикт в журнал задачи (числа ±%); само обновление основного венва /
   правки `voice_presets`/`cosyworker` — ТОЛЬКО после согласования с владельцем и отдельным
   коммитом; при смене звука (B/C/D-батч) — обязательный A/B на слух перед массовой генерацией.

- [ ] По каждому кандидату B/C/D: замер «после» в тех же единицах + процент разницы к базе.
- [ ] Качество: метрики WER/SS (или слушательский протокол) на выборке — цифры «до/после»,

- [ ] Вердикт: «обновлять с X% выигрыша» либо «не обновлять» — с причинами; статус DONE.
- [ ] Edge-cases: VRAM-конфликт с работающим po-переводом (замеры только при свободной
