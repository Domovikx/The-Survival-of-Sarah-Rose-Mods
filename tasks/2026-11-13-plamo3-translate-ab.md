# Ресёрч: замена переводчика на PLaMo 3 Translate (A/B) и Hy-MT2 через `--n-cpu-moe`

Статус: READY

## Задача от пользователя

«давай может ты пока задачу запиши на Пламо и давай попробуем llama.cpp с --n-cpu-moe
(эксперты в RAM) это чтото интересное я бы тоже поэкспериментировал. сейчас просто оформим
задачку соберем инфу, но скачивать и работать с этим будем после моей работы я потом скажу
когда.»

## Цель

Понять, есть ли смысл сменить переводческую модель на более новую, и получить проверяемое
сравнение на нашем корпусе, а не по карточке модели. Отдельно — измерить, даёт ли
`llama.cpp --n-cpu-moe` (эксперты MoE в RAM) рабочий режим для 30B-A3B на 16 ГБ VRAM.
Критерий «стало лучше»: меньше реальных ошибок на тех же строках при сопоставимой скорости,
без отказов и смягчения 18+.

## Контекст (что есть сейчас)

Проверено 2026-11-13 через HuggingFace API и GitHub API (веб-поиск недоступен).

- **Текущая модель**: `IndexTeam/Index-Translate-9B` (GGUF, опубликован 2026-10-02/03).
  150 языков, формат `instTrans` (жёсткие требования: глоссарий, формат; мягкие: стиль),
  мультимодальный mmproj. Размеры: Q4_K_M 5.78 ГБ, Q8_0 9.79 ГБ. Именно под её формат
  настроен `.opencode/skills/translate/tone_native.mts` (глоссарий имён, пол, словарь книги,
  запрет клиники).
- **Специализированных переводчиков на DeepSeek нет.** Поиск `deepseek + translation` на HF
  даёт только любительские LoRA (ru→en лирика), fasttext-файл и NSFW-файнтюн. В карточке
  Hy-MT2 DeepSeek упоминается лишь как бенчмарк-сравнение.
- **PLaMo 3 Translate** (`pfnet/plamo-3-translate-*`, PFN): GGUF-репозиторий создан
  2026-10-27, README обновлён 2026-11-09. Размеры 0.8B / 2B / 8B / 31B, 53 языка (все наши).
  GGUF Q4_K_M: 0.8B — 0.57 ГБ, **8B — 5.28 ГБ**, 31B — 19.53 ГБ (в 16 ГБ не влезет).
  32k контекст, глоссарий, surrounding context, история перевода, стиль (только для японского).
  Заявка PFN: 2B обгоняет специализированные LLM (включая HY-MT2 и TranslateGemma) по всем
  метрикам, 8B — сильнее. Лицензия PLaMo Community: личное/некоммерческое бесплатно;
  коммерческое — регистрация (бесплатно при выручке ≤1 млрд йен), выше — отдельный договор.
- **Hy-MT2** (`tencent/Hy-MT2-*`, Tencent, май 2026): 1.8B / 7B / 30B-A3B, 33 языка (все
  наши), 262k контекст. GGUF 7B: Q4_K_M 4.62 ГБ, Q6_K 6.16 ГБ, Q8_0 7.98 ГБ.
  **30B-A3B Q4_K_M = 18.24 ГБ** — в 16 ГБ целиком не влезает, только с offload экспертов.
  В карточке предупреждение: GGUF зависит от кастомного STQ-kernel (llama.cpp PR #22836);
  на 2026-11-13 PR **открыт и не смержен** — стандартный LM Studio может не загрузить файл.
  Рекомендованные параметры: temp 0.7, top_p 0.6, top_k 20, repetition_penalty 1.05 (не greedy).
- **TranslateGemma** (Google, янв 2026): 4B / 12B / 27B, gated-доступ, лицензия Gemma.
  12B Q4 ориентировочно 7–8 ГБ. Кандидат второго ряда.
- **Готовые сравнительные тесты есть, но все — от вендоров:**
  - Карточка `IndexTeam/Index-Translate-9B` (прочитано 2026-11-13) содержит прямое
    сравнение на своих метриках. Ключевое: Index-9B обгоняет Hy-MT2-7B и
    TranslateGemma-12B по WMT26 Judge (75.35 против 60.51 и 71.19) и по
    instruction-following (instTrans IFscore 0.8209 против 0.6079 и 0.3068);
    Hy-MT2-30B-A3B близко (66.81 / 0.6415), но это 18.24 ГБ. На low-resource
    Hy-MT2-7B проваливается (COMET 0.4626 против 0.7992 у Index).
    DeepSeek-V4.1-Flash и GPT-5.6-Sol сильнее по Judge, но это API/крупные модели.
  - Блог PFN (2026-11-05) заявляет, что вся линейка PLaMo 3 Translate обгоняет
    Hy-MT2 и TranslateGemma, но бенчмарки JP-центричные (PFTB, SaaS, WMT24++ EN→JA,
    FLORES+ chrF++ вокруг JP/EN). Отдельных цифр по EN→RU в тексте нет — только на
    графике. То есть для нашей пары направлений это пока непроверенное обещание.
  - Отчёты Hy-MT2 (arXiv 2605.22064) и Index (2609.40181) — тоже самозамеры.
  - Независимого head-to-head на нашей паре (EN→RU) и нашем жанре (18+ литература)
    нет. COMET/chrF его и не заменят: они меряют адекватность/беглость на
    новостях/вики, а не литературный регистр.
- **Железо**: RTX 5070 Ti 16 ГБ VRAM, 32 ГБ RAM. Сейчас GPU занят переозвучкой VoxCPM.
- **llama.cpp локально не установлен** (проверено 2026-11-13: `llama-server` не в PATH,
  в `C:/tools` только TTS-окружения) — для `--n-cpu-moe` его надо поставить отдельно.
- **Что уже проверено на нашем корпусе**: Index-Translate-9B — 205 якорных строк `ru`
  вычитаны, 16 реальных исправлений в 9 демо-языках после сплошного аудита; детектор
  регистра — 0. То есть базовая модель не «сырая».

## Что сделать (ресёрч, по протоколу `tasks/AGENT.md`)

1. Скачать и поднять кандидатов (после команды владельца):
   - PLaMo 3 Translate 8B Q4_K_M (5.28 ГБ) — LM Studio, GPU.
   - Hy-MT2-7B Q6_K или Q8_0 (6.16 / 7.98 ГБ) — LM Studio; отдельно проверить, грузится ли
     GGUF без STQ-kernel.
   - Hy-MT2-30B-A3B Q4_K_M (18.24 ГБ) — llama.cpp с `--n-cpu-moe` (эксперты в RAM),
     OpenAI-совместимый сервер на localhost.
2. Ответить на вопросы:
   - Грузится ли каждый файл в текущем LM Studio / llama.cpp, сколько VRAM/RAM занимает?
   - Какая скорость на нашей строке (с/строка) и сколько памяти остаётся?
   - Для `--n-cpu-moe`: сколько экспертов offload'ить, какой `-ngl`, какая скорость и
     деградация качества относительно Q4 на GPU?
   - Как передавать наши ограничения (имена, пол, словарь книги, запрет клиники) в
     PLaMo/Hy-MT2: у PLaMo — `target_lang`/`glossary`/`context` через system-сообщение или
     `chat_template_kwargs`; у Hy-MT2 — свой шаблон инструкции. Нужен ли адаптер промпта.
   - Как ведут себя модели на 18+ явном тексте: отказы, смягчение, цензура?
3. **Сначала отделить «модель» от «кванта»**: у нас стоит Index Q4_K_S. Прогнать тот же
   Index в Q6_K (7.56 ГБ) или Q8_0 (9.79 ГБ) — это тот же переводчик, просто точнее веса.
   Если разница с Q4_K_S заметна, часть остаточных ошибок — от кванта, а не от модели.
   По карточке PLaMo 8B: Q4_K_M теряет относительно BF16 около 0.0019 PFTB и 0.06 chrF++
   (в пределах шума), Q3_K_M — уже 0.0100 и 0.25, Q2_K — 0.0130 и 0.91. У Index в карточке
   GGUF прямо сказано: Q4_K_M «recommended», Q3 — «noticeable quality loss», Q2 —
   «significant quality loss», Q4_K_M сверяли с F16 и получили почти дословное совпадение.
4. A/B на фиксированном наборе: те же 50–100 якорных строк `ru` (можно взять
   `po_changed --lang ru --uids` + индексы), один и тот же промпт-каркас. Метрики:
   обратный перевод + F1, судья v13, ручная вычитка, число реальных ошибок. Сохранить отчёты
   в `tmp/` и цифры — в журнал задачи.
5. Сравнить варианты, сделать вердикт ±, зафиксировать условия пересмотра.
6. Если модель лучше — план интеграции: адаптер промпта, перенос `STYLE`/глоссария,
   переозвучка только якорных строк.
