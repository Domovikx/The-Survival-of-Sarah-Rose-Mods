# Task Creator (идея → задача в tasks/)

Оформляешь новую задачу так, чтобы любой агент (или человек) мог взять файл и выполнить его без
вопросов. Код не трогаешь, ничего не коммитишь — только markdown-файл задачи и строка в таблице
среза.

## 0. Прочитать правила проекта (обязательно)

1. `tasks/README.md` — статусы `READY → DOING → DONE`, DoD, коммиты.
2. `tasks/AGENT.md` — ресёрч-first: в задаче выборы оформляются как вопросы для ресёрча, а не как
   решённые назначения «по памяти».
3. `tasks/<текущий срез>/README.md` — таблица задач: занятые файлы, статусы, порядок по
   зависимостям.
4. Образцы стиля (не переписывать, а подражать): `tasks/mvp-2/archive/2.24-menu-apply.md`
   (ресёрч-задача), `tasks/mvp-2/archive/2.20-ui-scale.md` (выполненная, с доказательствами).

## 1. Извлечь из диктовки

Из реплики пользователя выдели: **цель** (что и зачем), **«как сейчас»** (что уже есть/чего нет),
**пожелания/примеры** (ссылки на прецеденты — сохрани дословно в цитате). Дословную цитату
пользователя вставь в секцию «Задача от пользователя» — она нужна, чтобы не потерять исходный
контекст при переделках.

Если не хватает данных для рамок задачи (что входит/не входит, где живёт, критерий успеха) — один
раунд `question-tool`, ≤5 вопросов, с рекомендацией в каждом варианте. Не выдумывай за пользователя
и не раздувай задачу уточнениями, на которые ответ найдёшь в коде (это шаг 2).

## 2. Собрать «как сейчас» по коду (ресёрч, не гадание)

Погрепай и прочитай затронутые места: факты — с привязкой `файл:строка`. Что смотреть минимум:

- `index.html`/конфиги деплоя — что уже есть (мета-теги, манифест, базовый URL);
- слайс из `docs/ARCHITECTURE.md` («куда класть») — в какую папку пойдёт реализация;
- похожие готовые решения в репо (паттерны, которые уже используем: сторы, persist, чекеры в
  `tmp/check/`).

Неизвестное не прикрывай домыслами — выноси в секцию «Что сделать (ресёрч)» как вопрос с гипотезой.
Чужие прецеденты, которые пользователь указал ссылкой, но ты их не нашёл в репо — тоже вопросом
(«найти/уточнить у человека»), а не молча пропускай.

**Вебсерч на этом шаге разрешён и приветствуется**: если что-то непонятно (как платформа поступает в
определённой ситуации, что поддерживает стандарт), либо хочешь найти лучшие практики/современный
подход/актуальный стандарт по теме задачи — гугли сразу, не откладывая в «ресёрч при выполнении».
Приоритет источников и дата сверки — как в `tasks/AGENT.md` (официальные доки/спеки → исходники →
сравнения → статьи). Факт из веба в задачу класть ссылкой и датой; непроверяемое — `[УТОЧНИТЬ]`.
Если `websearch` отдаёт 403 — обход через `https://html.duckduckgo.com/html/?q=` + `webfetch`
конкретных страниц (тот же протокол, что в AGENT.md). Такой предварительный веб-ресёрч кладётся в
задачу сжато (2–5 строк в «Контекст» или «Что сделать»), полный глубокий разбор с таблицей вариантов
всё равно происходит при выполнении задачи.

## 3. Номер и файл

- Номер = следующий свободный в текущем срезе (`tasks/mvp-2/`: максимум существующих + 1).
- Имя: `[YYYY-MM-DD]-kebab-case.md` — дата создания + тема (латиницей, коротко). Номера в имени
  больше нет: порядок/зависимости живут в таблице `README.md` среза; существующие задачи с номерами
  не переименовывать (новый формат только для новых).
- Путь: `tasks/<срез>/<файл>.md`.

## 4. Шаблон (канонический)

```markdown
# [YYYY-MM-DD] Глагол + объект: что именно делаем (коротко)

Статус: READY

## Задача от пользователя

«Дословная цитата того, что сказал человек — с примерами, ссылками, аналогиями.»

## Цель

3–6 строк: что хотим и зачем, для кого, критерий «стало лучше». Формат job story, если уместно:
«Когда <ситуация>, я хочу <действие>, чтобы <результат>».

## Контекст (что есть сейчас)

- Факты по коду с `файл:строка` (прочитано, не по памяти; дата проверки — сегодняшняя).
- Что уже сделано/готово из смежного, что чинить не надо.

## Что сделать (ресёрч, по протоколу `tasks/AGENT.md`)

1. Вопросы ресёрча: перечень того, что надо выяснить (формулировать как вопросы, не как «надо
   сделать Х» — решение принимается после таблицы вариантов).
2. Вебсёрч по бест-практикам темы; таблица вариантов ≥2, метод исключения, вердикт ±.
3. Реализация — после согласования ресёрча с человеком (вопросы через question-tool).

## Приёмка

- [ ] Пункты наблюдаемы/проверяемы («видно по факту», «тест падает/проходит»), не «работает
      аккуратно».
- [ ] Границы и edge-cases: что происходит при пустом/битом/отсутствующем входе.
- [ ] Тесты рядом (`*.test.ts`) для чистой логики; если UI — Playwright-чек без ошибок консоли.
- [ ] Полная батарея перед сдачей: `npx tsc --noEmit`, `npx eslint src/`, `npm test`,
      `npm run build`.

## Вне рамок (out of scope)

- Явный список того, что сознательно НЕ делаем (чтобы исполнитель не «додумал», и чтобы позже это
  нельзя было выдать за скрытое требование).

## Файлы (ожидаемые)

- `путь/к/файлу` — что в нём появится/изменится.

## Связи

- Смежные задачи/доки/спека (если есть `specs/`), иначе опустить секцию.
```

**Форматирование**: markdown-**таблицы в задаче не делать (бэд)** — контекст, варианты, кейсы и
edge-cases оформлять **списками** (буллиты/нумерация — бэст): списки не ломаются на diff'ах, не
расползаются на узких экранах и читаются скринридером. Единственная таблица, которую трогаем, —
строка в обзоре среза `README.md` (это не файл задачи). Таблицы «вариантов ≥2» из шага ресёрча —
работа при выполнении задачи, в сам файл задачи их не переносить.

## 5. Чек-лист качества (проверь до сдачи файла)

По бест-практикам (источники — в конце файла, сверены 2026-10-08):

- [ ] Заголовок — «глагол + объект», конкретный: «Добавить og:теги и картинку превью», а не
      «Улучшить превью».
- [ ] Приёмка — объективные условия, каждое можно проверить одним действием; ни одного «должно быть
      хорошо/красиво/быстро» без числа или наблюдения.
- [ ] Есть «Вне рамок» — граница против расползания объёма.
- [ ] Есть edge-cases/error-states хотя бы одним пунктом приёмки (самая частая дыра тикетов по
      SDD-исследованию).
- [ ] INVEST: задача закрывается часами, а не днями; если нет — предложи пользователю разбить на 2–3
      файла и обнови таблицу среза.
- [ ] «AI-prompt test»: агент, взяв файл, не обязан спрашивать про рамки — либо ответ в контексте,
      либо вопрос вынесен в «Что сделать (ресёрч)» через question-tool.
- [ ] Цитата пользователя дословная, статус `READY`, таблица среза дополнена строкой
      (`| NNN-name | READY | Задача |`).
- [ ] Никаких фактов «по памяти»: непроверенное помечено `[УТОЧНИТЬ]` или вопросом.
- [ ] В файле задачи нет markdown-таблиц (бэд) — везде списки (бэст); таблица только одна, в
      `README.md` среза (строка-обзор).

## 6. Финиш

1. Покажи пользователю: путь файла, 1–2 строками что в задачу попало, открытые вопросы ресёрча.
2. **Не коммитить** (СТОП-правило AGENTS.md) — коммит только по явной просьбе.
3. Правки самого скилла/агентов — напомни про перезапуск opencode (hot-reload нет).

## Источники бест-практис (ресёрч 2026-10-08)

- Ricardo Minas, «Writing tickets for Spec Driven Development» (2026-04): 6 частей тикета — Title
  (глагол+объект), Context (1–3 предложения, проблема и цена), Acceptance Criteria (проверяемые,
  построчно), Error States (самая частая дыра), Constraints, Out of Scope; тест готовности: «дай
  агенту без контекста — спросит ли лишнего».
- GitHub Spec Kit workshop, Tasks Phase: критерии INVEST (Independent, Negotiable, Valuable,
  Estimable, Small — часы не дни, Testable), задача = атом с чекбоксами приёмки, фазы и зависимости,
  чек-лист ревью (покрытие плана, объективные критерии, логичный порядок).
- Atlassian / ScrumChamps (2026-02): Given-When-Then как самый строгий формат AC — применять
  точечно, где поведение неоднозначно; не превращать весь файл в Gherkin.
- Домашние источники: `tasks/AGENT.md` (ресёрч-протокол), `tasks/README.md` (статусы/DoD), примеры
  `2.20`, `2.24`.
