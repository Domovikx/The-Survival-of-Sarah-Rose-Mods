## Что делает

`arc_branching.mts` строит модель арочного графа. **Единственный источник
истины — сама игра** (`game/*.rpy`, мимо `tl/`, `mods/`, `renpy/`; читает
`collectRpyFiles` из potgen): промежуточных артефактов нет, `template.pot`
в построении НЕ участвует (2026-10-29, требование владельца).

- **Переходы** — реальные `jump <label>` / `call <label>`: засчитываются
  только внутри блока своего `label`; цель обязана быть определённым
  label (иначе `call screen foo` дала бы фейковую арку)
- **Правило «лейбл → арка»** — `arcOfLabel` из `renpy-po/potgen.mts`
  (ARC_BY_LABEL/ARC_BY_PREFIX: арка выводится из имён лейблов самой
  игры) — DRY: диаграмма и POT используют ОДНИ правила и не могут
  разойтись после их правки
- **Галерея/реплеи** (`NO_ARC_FILES`) и `splashscreen` арок не несут —
  как в POT

На выходе — **state diagram** с уровнями:

- **Узел** = арка (`Prologue`, `UnionKingdom`, …)
- **Уровни** = BFS-глубина от стартовых арок («старт > арка > арка > …» с
  видимым ветвлением, а не плоская каша)
- **Ребро** = переходы между арками, вес = сколько `jump/call` ведут в арку
- **Сплошная стрелка** — вперёд (на следующий уровень),
  **пунктир `N↩`** — возврат/петля (на свой уровень или выше)

Важные факты, которые подтверждены тестами:

- **Нотация — только state diagram.** `activity-beta` (`label`/`goto`/
  `if`/`detach`) падает в превью `jebbs.plantuml` с `Syntax Error
(Assumed diagram type: activity)` — это проверено и потому не
  используется (2026-10-29).
- **Диаграмма детерминирована** — байт-в-байт одинаковый рендер для одних
  и тех же данных (юнит-тест на это есть).
- **Фактические размеры игры:** 247 сюжетных лейблов → 19 арок, 37
  межарочных перехода, 5 уровней.

## Запуск

```bash
# ОПТОМ с POT (рекомендуется: potgen уже сканирует те же файлы игры —
# POT и диаграмма физически не могут разойтись)
npm run potgen
#   -> patches/ai-voice-pack/po/template.pot
#   -> docs/game-branching.puml        (флаги: --puml <файл> | --no-puml)

# сам по себе (только диаграмма)
node .opencode/skills/arc-branching/arc_branching.mts

# свой путь к игре / выходной файл
TSSR_GAME="D:/Steam/steamapps/common/The Survival of Sarah Rose/game" \
  node .opencode/skills/arc-branching/arc_branching.mts --out tmp/branching.puml
```

Диаграмма открывается в VS Code нативно: открыть `docs/game-branching.puml`
→ `Alt+D` (превью `jebbs.plantuml`; настройка рендера через сервер —
`plantuml.render: PlantUMLServer` в `.vscode/settings.json`).

## Тесты

```bash
# юнит: парсеры, граф, уровни, рендер (без игры)
node --test .opencode/skills/arc-branching/arc_branching.test.mts

# e2e: против реальной установки (без игры — скип)
node --test .opencode/skills/arc-branching/arc_branching_e2e.test.mts
```

**e2e включает гард актуальности:** коммиченный
`docs/game-branching.puml` обязан байт-в-байт совпадать со свежей
генерацией. После апдейта игры (перегенерирован POT / изменены переходы)
тест падает с просьбой перегенерировать — это и есть «диаграмма протухла».

## Когда обновлять

- **апдейт игры** (изменились `jump/call` или поменялись лейблы) —
  перегенерировать диаграмму и закоммитить вместе с обновлением;
- **правка маппинга арок** (`#. label-map:` в POT) — то же самое.

## Границы

- Диаграмма **только про архитектуру ветвления**: счётчиков строк/фраз,
  Vox/cosy-статусов в ней НЕТ (по требованию владельца 2026-10-29 —
  «мне не надо что озвучено, мне нужно ветвление арок от исходника
  игры»).
- Пути `jump` к неизвестным label и петли внутри одной арки в граф не
  попадают (сознательно: это не архитектура переходов между арками).
- Игра читается только на чтение; ни один файл игры не изменяется.
