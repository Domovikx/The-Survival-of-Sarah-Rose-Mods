# MAP — translate (построчный перевод)

Факты и грабли, проверенные практикой. Формат: симптом → причина → проверено → что делать.

- **`po/<lang>.po` стал нулями (размер есть, содержимого нет)** → процесс
  перевода убили посреди записи (перезапуск сервера/сессии, kill), и запись шла
  НЕ через `writePoAtomic` (или через сторонний writer). Проверено 2026-11-15:
  `zh.po` = 11 102 280 байт нулей, 0 msgid. Что делать: `git status` покажет
  файл как изменённый → `git checkout -- patches/ai-voice-pack/po/<lang>.po`
  (в HEAD всегда целая версия), затем `npm run po:check`; незакоммиченный
  прогресс при этом теряется — поэтому после каждого крупного батча делай
  коммит `chore(po): <lang> — прогресс N/M`.
- **`grep -c '^msgstr ".\+'` врёт, что «переведено всё»** → в BRE `.` совпадает
  с закрывающей кавычкой, поэтому пустой `msgstr ""` тоже считается (2026-11-15
  этой проверкой пустые de/es/fr/it/ja/ko/pl/pt выглядели полными) → считать
  через `node scripts/po_check.mts --all` (он печатает «пустых N») или
  `grep -c '^msgstr ""$'`; на глаз — именно пустые, не непустые.
- **После `git checkout -- po/<lang>.po` `npm run po:check` пишет «файлов
  к проверке нет»** → проверяются только ИЗМЕНЁННЫЕ против HEAD файлы, а
  восстановленный файл байт-в-байт равен HEAD → для проверки восстановленного
  звать `node scripts/po_check.mts --all` (2026-11-15: 10 файлов целы).
- **`tmp/translate_<lang>.done` после аварии забит нулями и обрезан** (проверено
  2026-11-15: 17 КБ нулей, 53 339 строк против 54 683 заполненных в po) → чинить
  не нужно: `po` — источник истины, `done` только кэш (пропуск идёт и по
  непустому `msgstr`); прогресс/скорость смотреть `translate_ctl status`.
- **Перевод ушёл на общую модель (Strata/Qwen3.6) вместо переводческой** → раннер
  брал бэкенд из пульта (`resolveBackend()`), а пульт переключали под чат/эмоции.
  Проверено 2026-11-15: прогон `zh` дошёл до 94 % на `qwen3.6-35b-a3b-ud-q4_k_xl`.
  Что делать: перевод и судья теперь зовут `resolveTranslateBackend()`
  (`translate_backend.mts`) — дефолт `index-translate-9b` в LM Studio `:1234`,
  пульт на них не влияет; оверрайд только `--model`/`--base-url` или env
  `TSSR_LLM_MODEL`/`TSSR_LLM_URL` (+ `⚠ НЕ переводческая модель` в шапке).

- **Почему перевод вообще оказался на Strata (первопричина 2026-11-15)**: и
  `translate_run`, и судья, и правки регистра (`tone_fix`/`tone_native`) брали
  бэкенд из пульта (`resolveBackend()`), а пульт с 2026-11-01 по умолчанию —
  Strata (`qwen3.6-35b…`). Достаточно было один раз не переключить пульт.
  Убито в корне: все переводные тулы зовут `resolveTranslateBackend()`
  (дефолт `index-translate-9b`), в раннере — STOP на не-переводческой модели,
  **обходного флага нет**. Проверка: `TSSR_LLM=strata` больше не влияет
  (2026-11-15), `TSSR_LLM_MODEL=qwen3.6…` → STOP. На пульте остались только
  эмоции (`emotion_tag`/`emotion_judge`) — это не перевод.

- **Прогон стоит в `[BACKEND-DOWN]`, сервер LM Studio «сам» падает** → сервер
  живёт в GUI-приложении (закрыли окно / приложение завершилось — сервер умер),
  версия тут ни при чём. Проверено 2026-11-15. Что делать: поднять headless
  `llama-server` из бэкендов LM Studio на `:8081` (команда — SKILL «Стабильный
  бэкенд») и гнать прогон с `TSSR_LLM_URL=http://127.0.0.1:8081
TSSR_LLM_MODEL=index-translate-9b`. Загрузка модели ~5 мин, до этого 503.
- **Судья на zh даёт ~90 % ложных флагов** (калиброван на ru): из 26 флагов
  волны реальных было 4. Проверено 2026-11-15. Что делать: флаги судьи читать
  глазами перед `--retrans`; детерминированные классы (`РУССКИЙ ТЕКСТ`,
  `[АНГЛИЙСКИЙ]`, `ЛАТИНИЦА` — последняя только для CJK) — доверять,
  они без ложных.

- **Пул пустых строк, которые «не переводятся» пассами** → модель ВКЛЕИВАЕТ
  текст следующей реплики в конец предыдущего перевода (RL-баг «дописывает
  соседа»): строка `i` пустая, её текст уже в `i-1`. В логе — череда
  `ОШИБКА … вклейка соседней строки`. Проверено 2026-11-16 на `es` (444 пустых,
  скорость пассов упала до 0.01 стр/с). Что делать: сначала
  `translate_salvage.mts <lang> --apply` (перевод 1:1 без контекста — склейка
  невозможна), ПОТОМ `--retrans` по склеенным ПРЕДЫДУЩИМ строкам. В обратном
  порядке `--retrans` буксует: гейт вклейки видит тот же грязный сосед.
- **`[СКЛЕЙКА]` в `translate_review` считает хвостовые многоточия отдельными
  предложениями** → на `ru` давало 59 ложных (`Лили! Ты же не собираешься...`).
  Проверено 2026-11-16. Что делать: `sentences()` сначала срезает хвост
  `[.…\s-]+$`; плюс склейкой считается только строка, где в ОРИГИНАЛЕ есть
  хотя бы одно законченное предложение (иначе «Sixteen» → «Шестнадцать.»
  ловилось как склейка).
- **`[ЛАТИНИЦА]` давал 67 950 ложных на `es`** → класс писался как «в переводе
  нет кириллицы», а это осмысленно только для CJK. Проверено 2026-11-16.
  Что делать: `CJK = zh|ja|ko`, проверка латиницы/иероглифов — только под ним.
- **Баг «перевёл не на тот язык»** (был раньше) → проверить, что язык назван
  в промпте ЯВНО. Проверено 2026-11-16: `translate_run` подставляет
  `TARGET[LANG]` и в system-промпт, и в `STEP 2 — TRANSLATE ONLY the EN line
into …`; язык нигде не выводится из контекста. Дополнительно в ревью есть
  класс `[АНГЛИЙСКИЙ]` (2–3+ частых EN-слова подряд в не-EN переводе).

- **Скорость бэкенда: что уже проверено и отклонено** → см.
  `docs/translate-backend-perf.md`. Коротко: `--spec-type ngram-simple` даёт
  acceptance 0.66, но по факту 124.9 tok/s против 129.2 у базового конфига
  (не используем); `temperature 0` НЕ детерминирован (батчинг) — побайтовое
  A/B переводов бессмысленно, сравнивать только мс/токен и смысл; оперативка
  скорость не даёт (модель целиком в VRAM).

- **Язык «брошен» с дырами: очередь ушла дальше, оставив пустые строки** → очередь
  делает до 30 пассов на язык; если прогресса нет, зовёт
  `translate_salvage.mts <lang> --apply` (перевод 1:1, склейка невозможна), затем
  один обычный пасс; если остаток остался — пишет `tmp/translate_<lang>.stuck.txt`.
  Причина пустот — вклейка соседней строки (модель «дописывает» соседа, гейт
  отклоняет, и в контексте она видит уже испорченного соседа → повторяет ошибку
  вечно). Проверено 2026-11-16 на `pt`, 2026-11-17 на `de` (127 строк).
  Руками то же самое: `translate_salvage <lang> --apply` → `translate_review <lang>
--all` (классы `[УТЕЧКА]`/`[СКЛЕЙКА]`) → починить склеенных соседей.
- **Процесс очереди, запущенный ДО фикса, продолжает работать по-старому** →
  `de` ушёл на 30-пассовом капе и был брошен с 127 дырами, хотя в коде уже было
  автоспасение: живой процесс держит старую версию скрипта в памяти (Node читает
  файл при старте). Поймано 2026-11-17 по фразе в логе, которой в текущем коде
  нет. Что делать: после правки кода очереди — перезапустить её (и проверить,
  что в логе новые формулировки), а не ждать, что подхватит само.
- **Гейт вклейки СЛЕП, когда сосед ещё пуст** → детектор сравнивает перевод с
  переводами соседей; если сосед ещё не переведён, сравнивать не с чем, и модель,
  вернувшая соседнюю строку, проходит гейт молча. Результат: строка X получает
  перевод X+1, а X+1 остаётся пустой. Поймано 2026-11-17 на `de` (313 флага
  механического ревью). Лечение: `translate_review <lang> --all` → индексы →
  `translate_salvage <lang> --indices tmp/<lang>.fix.txt --apply`. В
  `translate_salvage` с этой даты стоит гейт соседей (`commonRun`/`sharePhrase` из
  `review_common_run`), поэтому повторная запись склейки невозможна.
- **Ложные флаги ревью по языкам** (проверено 2026-11-17, `--all` по всем 10):
  `[УТЕЧКА]`-«вклейка» на `ru` ловится на повторяющихся оборотах («сара
  чувствовала как», «по всему городу») — все 259 флагов оказались чистыми;
  `[СКЛЕЙКА]` на `de` — на многоточиях («Ich... Entschuldigung?!» = +1
  предложение), все 19 чистые; `[ЛАТИНИЦА]` на `ja`/`ko` — законные латинские
  имена в меню. Что делать: смотреть глазами, в хардкод-списки не заносить
  (правило владельца: тюнинг промпта, не индексы). Настоящий брак в тех же
  прогонах был: 6× «サrah» (катакана+латиница) в `ja`, 3 строки не своего
  оригинала, `mob` внутри корейской строки — исправлено.
- **po обнулился «правильного размера» (9 МБ нулей, 0 msgid)** → жёсткое убийство
  процесса (TerminateProcess, в т.ч. при перезапуске сервера/ребуте) до того, как
  NTFS сбросила данные из кэша: `rename` был, а данных на диске ещё нет. Поймано
  дважды: `de.po` 2026-10-26 и `ja.po` 2026-11-17 (плюс `tmp/llama_spec.out.log`
  в тот же момент — то есть страдали все недавно писанные файлы). Что делать:
  `writePoAtomic` теперь пишет `.part` через `fsync` и после rename проверяет
  первые 32 байта на нули — потерять можно максимум текущий батч, файл остаётся
  прежним. Восстановление: `git checkout -- patches/ai-voice-pack/po/<lang>.po`
  (теряется работа после последнего коммита) и перезапуск очереди — она resumable.
  Ещё: НЕ гонять очередь в фоновом шелле агента — его убивают жёстко; запускать
  отдельным процессом (`Start-Process node … -WindowStyle Hidden`).
- **Жёсткие ребуты ПК во время прогонов (Kernel-Power 41, без BSOD/WHEA)** →
  2026-11-17 случилось три за ~15 минут при перезапусках очереди. Такой профиль —
  потеря питания (скачок GPU/PSU) или тепловая защита, а не «синий экран»: дампа
  нет, в журнале только 41. Что делать: держать запущенным
  `node scripts/health_guard.mts --interval 15` — он пишет `tmp/health.csv`
  (GPU temp/Вт/util/VRAM, CPU%, RAM, диск) с fsync каждые 15 с и при выходе за
  порог (GPU ≥ 85 °C, RAM ≤ 10 %, диск ≤ 5 ГБ) сам гасит очередь и llama-server.
  Замеры 2026-11-17 под нагрузкой: GPU 61–65 °C при 254–260 Вт (лимит 300) —
  то есть перегрева нет, а вот питание близко к потолку; подозрение на PSU и
  транзиенты. Очередь запускать ОТДЕЛЬНЫМ процессом (`Invoke-CimMethod
Win32_Process Create` или ярлык), не в фоновом шелле агента.
- **Коммит во время прогона ТЕРЯЕТ переводы** → хук делает `npx lint-staged`, а он
  перед задачами прячет НЕиндексированные изменения в `git stash`. Задача упала →
  коммит прерван, восстановление оставило «lint-staged automatic backup», а `pt.po`
  вернулся к HEAD: 59 свежих строк «исчезли». Проверено 2026-11-16 (нашлись в
  `stash@{0}`). Что делать: в хуке стоит `lint-staged --no-stash` + гейт
  `scripts/po_live_guard.mts` (блокирует коммит po при живом прогоне). Восстановление:
  `git stash list` → `git checkout 'stash@{0}' -- patches/ai-voice-pack/po/<lang>.po`
  → `node scripts/po_check.mts <lang>`. Осознанный обход гейта:
  `TSSR_COMMIT_WHILE_TRANSLATING=1 git commit …`.
- **`lint-staged` сам ставит в индекс po, который пишет очередь** → после задач он
  делает `git add` по файлам, чей НЕиндексированный diff изменился за время задач
  (логика «застейджить правки, сделанные задачами»). Очередь пишет `po` каждые пару
  секунд → файл попадает в коммит, и гейт справедливо его блокирует (наблюдалось
  2026-11-17 на `ja.po`, 11 018 строк). Что делать: при живом прогоне коммить
  **без хуков** — `git commit --no-verify` после ручных проверок (oxlint/prettier/
  markdownlint/`npm run typecheck`/тесты), предварительно убедившись, что в индексе
  нет `po/*.po` (`git diff --cached --name-only | grep '\.po$'`). Переменная
  `TSSR_COMMIT_WHILE_TRANSLATING=1` в этом случае НЕ спасает: она снимает блок гейта, а
  `po` уже в индексе — то есть уедет в коммит.
- **«Пустых строк» столько же, сколько в логе, но `git status` чист** → рабочий
  `po` мог откатиться к HEAD из-за стеша (см. выше): сверять не `grep`, а
  `parsePo` + `git diff --stat`.

- **Судья на `pt`: «Inverted gender» бывает ложным** → «I'm a princess…» / «You were
  one…» — местоимение согласуется с СУЩЕСТВИТЕЛЬНЫМ (princesa → uma), а не со
  спикером. Проверено 2026-11-16. Что делать: такой флаг сверять с предыдущей
  репликой, где назван предмет/роль.
- **Судья на `pt`: «Invented meaning» по синониму** → «to unmake her» → «destruir»
  формально близко, но замысел («развоплотить») теряется; правка на «desfazer».
  Флаг полезен как подсказка оттенка, не как ошибка.

- **После сбоя со стешем пропали НОВЫЕ файлы (тестов), а легаси-аудио вернулось** →
  `git stash` по умолчанию НЕ берёт untracked-файлы, поэтому свежесозданные тесты
  восстановить из стеша нельзя; а трекаемые файлы в рабочей копии откатываются к
  HEAD. Проверено 2026-11-16/17: пропали `voice_stale.test.mts` и
  `voice_corpus.test.mts` (воссозданы вручную), вернулись 62 удалённых легаси-файла
  озвучки (оказались побайтовыми дублями — удалены). Что делать: после любого
  инцидента с хуком/стешем сверять `git status` и наличие новых файлов, а не
  только содержимое po; `git stash show --stat 'stash@{0}'` покажет, что там есть.

- **«Пассы без прогресса» + `ОШИБКА [N] … похоже на перевод соседней строки`** →
  перевод строки N лежит в строке N−1 (сдвиг на одну вверх), валидатор видит
  «кандидат = текст соседа» и запирает строку навсегда. Проверено 2026-11-18 на
  pl: у всех 114 застрявших строк предшественник был заполнен ИХ переводом.
  Две причины сложились: салваж ловил только дословное совпадение (парафраз
  проходил мимо), а очищенный донор не возвращался в работу, потому что его
  индекс лежал в `tmp/translate_<lang>.done` (раннер пропускал пустую строку по
  кэшу). Что делать: `translate_salvage.mts <lang> --indices
tmp/translate_<lang>.stuck.txt --apply`, затем обычный прогон, затем
  `po:check`; правило «пустота важнее кэша» в раннере не откатывать. История
  инцидентов — `docs/translation-incidents.log`.

- **Обрывочные реплики после сплита строки в игре** (`I...` + `Think that is a
wonderful idea, Sarah.`) → модель с контекстом склеивает обрывок со следующей
  строкой, гейт видит вклейку и строка стоит. Проверено 2026-11-18 (pl: 22
  строки, все закрыты сбоев 0). Что делать: тот же салваж — перевод 1:1 без
  контекста и соседей; для фрагментов это единственный надёжный путь.

## Многоязычность: N языков усложняют не объём, а проверки

Корпус — 69 120 строк × 10 языков. Умножение объёма предсказуемо; вертикальные
правила — нет: почти каждая эвристика калибрована на русском, и на других языках
она либо не срабатывает, либо ловит ложное. Это и есть источник «плавающих»
багов: один и тот же код ведёт себя по-разному на 10 языках.

Где это уже било:

- порог «вклейки соседа» (`commonRun`): на ru хватает 3 слов с ≥2
  содержательными, для романских/германских порог 6 слов, иначе ложные
  срабатывания на естественных коллокациях; для CJK словесное сравнение не
  работает вообще (нет пробелов);
- список стоп-слов только русский → «содержательных слов» на других языках
  считается неверно, поэтому в проверках он отключён (иначе ложные флаги);
- маркеры отрицания и «ты/вы» реализованы только для ru: для остальных 9
  языков этот класс ошибок не покрыт вообще;
- канон имён/глоссарий строится из русского корпуса — для pl/de/fr/it нужен свой
  (иначе имена «не узнаются» и проверки молчат);
- судья калиброван на ru (E2E-матрица 64 дефекта); на 9 других языках его порог
  не проверялся — флаги читать как подсказку, а не как приговор;
- сходство переводов (dice/commonRun) требует разных порогов по языкам: один
  порог на все 10 даёт либо пропуски (pl, 0.36–0.48), либо ложные очистки;
- ниже по конвейеру то же самое: CJK-кегли, субсеты шрифтов, рефы голосов,
  длина/паузы озвучки — каждое правило отдельное на язык.

Правило: правку в валидаторе, салваже или ревью проверять минимум на двух типах
языков (славянский/германский + CJK), прежде чем считать её общей. Настройка,
удобная для ru, на ja/ko обычно не работает вовсе; и наоборот — то, что
закрывает pl, может дать ложные срабатывания на ru.
